# Module Design Review

用于在生成视觉方向稿前审查 Architecture Map，并在方向稿生成后验证设计假设。目标是在低成本阶段消除会导致 HTML 明显返工的怪异布局，不把方向稿提高到设计师终稿精度。

## 先建立上下文

每个 Section 在确定 Layout 前先明确：

- 当前页面的任务和模块位置；
- 模块是核心证明、重要支撑、辅助说明、过渡还是转化收口；
- 访客看完后只需记住什么；
- 内容之间是并列、主从、分类、过程还是对比；
- 前后 Section 已经说明或证明了什么。

不得从模板外观反推模块任务，也不得为了填满一种 Layout 而增加内容或制造主次。

## 页头、首屏与切换模块（适用时）

- 完整页面涉及 Header 时，在 Map 中明确它与 Hero 是正常排列还是覆盖，以及初始/滚动后背景、文字图标反差、手机菜单和内页处理。用户已指定不重叠时原样传递，不把 Header 当 Hero 图片的附属层。
- 重要展示模块用代表性桌面视口宽高与实际文案判断比例：主体、名称、必要判断信息和主要动作能否同时理解。不能为一屏塞满而缩小核心图片或正文；手机可分段但应保留清晰的操作关系。
- 切换控件应在被切换对象附近可见、可操作；定义当前状态及边界行为，不把下一屏的标签作为唯一入口。
- 背景文字、相邻图片、投影与分隔线不得侵入阅读和操作区；若设计为局部裁切，明确保留的主体与边缘过渡，避免硬切关键轮廓。

这些是方案检查，不是浏览器实现验收；不规定所有 Header 不透明、所有商品左右布局或所有模块必须一屏显示。

## Module Solution Qualification

每个 Section 在选定 Layout 和生成方向稿前，必须通过以下门禁：

- 明确回答一个真实客户问题或顾虑；
- 已决定信息的主次、合并、关联、证据归属和扫读顺序；
- 存在与内容任务匹配的视觉叙事，不只有风格形容词；
- UI Composition 说明元素如何形成一个视觉整体，不只列出 Grid、Split、Timeline 或 Carousel；
- 已定义主焦点、视觉重量、弱化内容与 CTA 归属；
- 已处理相邻 Section 的重复、衔接与焦点竞争；
- 桌面与移动端的组织方式都保留原有信息叙事；
- 包含会导致错误结果的禁止方案和可观察的成功标准；
- Motion 默认可省略；若提出可选 Layer 2/3，必须有明确目的与移动端/Reduced Motion fallback，不以统一淡入替代设计判断；
- 能直接编译为生图提示词，无需执行者再决定卡片形式、证据位置、信息主次或视觉主线。

验收测试：两位设计师依据同一方案，应得到相同的信息结构、视觉主线和重点，只在样式细节上存在差异。只提供 Layout、栏位数量或组件名称的 Section 不合格。

## 四层判断

### 1. Commercial Job

- 模块是否快速回答 Page Content 规定的问题；
- 当前位置是否需要这个模块；
- 模块高度、强对比和交互成本是否与其业务重要性匹配；
- 辅助提示或次要 CTA 是否被过度设计。

### 2. Evidence Structure

- 主张是企业自述，还是有产品、工厂、设备、人员、数据、文件或案例支持；
- 证据类型是否适合当前任务；
- 重要证据是否获得足以查看和识别的尺寸；
- 生成图是否只是明确占位，而非暗示真实企业证据。

### 3. Information Geometry

- Layout 是否匹配真实条目数量、长度、媒体方向和内容关系；
- 并列内容是否被无理由地做成永久主次；
- 短数据或短标签是否因平均分栏产生大片无意义空白；
- 图片、文字、数据与 CTA 的面积是否反映信息优先级；
- Card、Viewer、Carousel、Accordion、Grid 或简单内容带是否有明确的内容理由。

对选型、入口、概览和流程等需要扫读的模块，检查标题、关键词、数据或操作入口能否先呈现必要的分类、区别、顺序或下一步；说明文字应补充必要判断，而非重复标题。短标签须增加识别价值，不只是给长句加外框；缺乏真实差异时不靠重复标签或编造参数填满版面。定义、FAQ及深入解释模块不要求脱离正文理解全部内容。内容已足够时允许紧凑表达，删去重复文字后不保留原描述的空位，也不为了卡片变矮缩小有用产品图。

### 3A. Media Fitness

- 产品图片、并列分类且图片能帮助识别时，优先比较 Gallery Grid；不得无理由压成小缩略图 + 长文字。
- 小缩略图 + 右侧文字只适用于图片为辅助索引、文字承担主要判断的模块。
- 多张等权工厂或设备图优先等权 Grid、Carousel 或可切换到同等查看尺寸的 Viewer。
- 证书与文件优先保持真实文件方向和比例，并提供足以辨认机构、标题或编号的查看方式；按需支持 Lightbox 或大图查看。
- Layout 是否符合 Media Display Contract 的原始形态、推荐比例、最小有效查看尺寸、视觉权重、同屏数量和移动端组织。

用户明确保留照片或后续提供真实图片时，精简文字不能改成小符号方案；素材未齐按已确认用途占位。无识别/证明需求时不强制配图。采用单项展开与换图时，记录默认、再次选择、媒体/图注对应、手机及缺图处理；状态规则与可选过渡分开，不因此新增动效门禁。需要同时比较的短内容可保持平铺，不强制手风琴或逐项配图。

### 4. Visual and Page Context

- 当前 Section 与前后模块是否重复大图、KPI、Logo、Card Grid、CTA 或强 Surface；
- 当前视觉重量是否匹配它在购买决策中的价值；
- 一个视区是否只有一个主焦点；
- 素材比例、密度和留白是否让模块可扫读；
- 移动端降级是否保留原有信息优先级。
- 加强评审页面的 Distinctive Concept 是否在首屏后继续通过真实证据、构图关系或节奏被理解，而不是后续全部退回相同三列卡片；
- 是否出现无理由渐变/发光、所有内容卡片化、通用图标方块、重复眉标—标题—描述或相同 Reveal；
- 保留的常见模式是否有明确的信息、媒体、品牌或操作理由。

### 5. Motion Fitness（按需）

- 动效是否服务理解、状态、承接或单一品牌记忆，而非掩盖静态构图问题；
- 已确认显式 Layer 2/3 时，Page Motion Budget 是否避免多个 Signature、多个持续媒体或相邻运动焦点竞争；
- Layer 2 是否只用于有顺序或叙事价值的内容，不机械覆盖所有 Section；
- Trigger、运动对象、Sequence 与 Section Job 是否一致；
- Mobile、Reduced Motion 与静态 fallback 是否保留内容、证据和 CTA；
- 图片方向稿没有被当作时间行为的证明。

前一层明显不成立时，不应先用配色、圆角、阴影或动效修补。

## 通用处理原则

- 证据应靠近它所支持的主张，避免无上下文 KPI、Logo 或文件。
- 一个视区只保留一个主焦点；标题、图片、数据和 CTA 不同时使用最高强调。
- 变化应服务内容关系，不为追求“每模块都不同”而制造新奇结构。
- Section 高度由信息与证据价值决定，不用固定高度、标准 Padding 或平均分栏强迫填满。
- 与前后内容重复时先删除、合并或迁移，不用卡片、换色、阴影或装饰掩盖结构问题。

## Architecture Map Review

在将 Map 交给用户确认之前，先对每个 Section 执行 Module Solution Qualification，再执行四层判断和整页检查：

- 页面顺序是否符合访客理解与决策过程；
- 加强评审页面的 Page Visual Throughline、Hero Structure、Signature Visual Device 与 Whole-page Continuity 是否具体、可由真实内容支持，并通过同行替换检验；
- 核心、支撑、辅助与转化模块是否形成合理强弱；
- 连续 Section 是否重复相同证据、构图或视觉重量；
- 推荐 Layout 是否有内容关系和证据需求支持；
- 已确认显式 Layer 2/3 时，其 Motion Budget / Intent 是否足够交给 HTML 实现；未采用时不要求 Motion 字段；
- UI 执行者是否仍需要重新猜测信息主次、证据归属、扫读路径、视觉叙事、查看方式或模块重量。

明确问题自动修正一轮后再交给用户。多个 Layout 都能合理完成任务时，提供建议、理由和影响，不自动追求唯一答案。

## 方向稿综合评估

参考粗方向图进入方案或 HTML 前，用当前实际画面、真实内容、Design System、模块任务及必要的相邻上下文做判断。用户反馈是重要输入，AI 也要主动判断，不把“用户没提”或“生成图已出”当作合理性证明。已完成且确认的 HTML 只在用户要求的范围评估，不因新增规则重做。

- **用户意见**：分清明确要求/锁定选择、满意之处、不满意之处和供参考的想法。保留其意图与素材要求，不把一句“有点平淡”直接翻译为加图片、卡片或动效。
- **AI 观察**：独立看模块在解释什么、第一眼看到什么、图片是否帮助理解、内容是否拥挤或空泛、重点是否被削弱，以及与前后模块的重量关系。以可见现象和阅读/操作影响说明理由；不能只数条目、复述 Map 或用“更高级”代替判断。未看见的手机状态或素材细节标为待验证。
- **综合决定**：结合两者形成“保留什么、改善什么、先确定什么”，说明为何采用以及如何处理。合理设计可直接保留，不为证明主动设计而更换；有问题但用户未指出时也应主动提出。

在现有 Map/Brief 或 Notes 内，只为需要解释的模块紧凑写明“用户意见（无则说明）→ AI 观察 → 采用决定与理由”。可用短段落或表格，不强制每模块填表或另出报告。保留用户要求、AI 建议、已采用决定之间的区别：

- 双方一致：写成具体可执行方案；已明确授权的选择直接采用，不重复确认。
- 用户提出候选想法：结合内容判断适用性，指出收益与代价，再推荐，不一概附和，也不擅自视为锁定。
- 双方存在分歧：指出具体冲突与影响，尊重用户明确决定；尚未选择且影响任务、主次、主要布局、媒体用途或必要交互时，集中确认。
- 只有字号、比例、裁切、密度和留白等未锁定细节：写为 HTML 改善项，由 Prototyper 实现并在浏览器核实。

评估结论应回答“为何保留或改变”，并交接已锁定决定、HTML 改善项、重要待定项。主要方案需改变时先更新受影响方案并确认；不自动重新生图。用户要求精确还原时，评估可提出风险和建议，不能因此自行释放其精确约束。以下 Visual Direction Review 与 A/B/C 分流用于落实这些判断。

## Visual Direction Review

生图后把 `Structure Fidelity` 与 `Visual Language Approval` 分开记录。用户认可配色、图片风格或设计感，不代表错误的 Section 身份、条目、证据或信息关系已确认。先检查结构，再检查 Solution Fidelity、Map Fidelity 和 Media Fitness：

- Section Job 是否一眼可见；
- 单一记忆点、视觉叙事和推荐扫读路径是否被清晰呈现；
- 数据、证据和 CTA 是否仍归属于方案指定的步骤或主张；
- 证据是否真正可看，而不只是存在；
- 内容关系和视觉主次是否一致；
- 模块高度和强度是否匹配业务价值；
- 相邻 Segment 的 Section 边界、Surface 与前后节奏是否成立；
- 是否出现为了“丰富”而增加的无价值图片、卡片、序号或装饰。

本轮审查在现有 Map / Notes 中简短指出实际可见的重点与需修正之处，不新增报告、表单或确认轮次。方案阶段说明计划如何露出重点；生图后须检查画面本身，不能仅以“条目齐全”或重述方案判为通过。不同类别的分组提示是否清楚、当前段与直接相邻段的密度是否协调，也应以画面为依据。单纯换色或换表格风格不自动构成结构失败；按现有 A/B/C 规则区分任务问题、实现细节与生成噪声。

方向稿不需要精美。Review 只需阻止会导致 HTML 明显返工的设计问题。

## 问题分流与停止条件

### A. 必须在 HTML 前处理

- Section 只有 Layout、栏位数量或组件名称，未形成合格的 Module Design Solution；
- 模块任务、证据类型或内容关系明显错误；
- 方向稿虽还原 Layout，但丢失视觉叙事、扫读路径、证据归属或单一记忆点；
- 并列证据被无理由地做成永久主次；
- 核心证据过小、不可查看或被装饰取代；
- 次要模块重量过高，或核心模块被过度压缩；
- Motion Purpose、Layer、Signature 或移动端动态叙事缺失/错误，迫使 HTML 阶段重新设计；
- 前后模块明显重复、争抢焦点或破坏页面叙事。
- 图片低于 Media Display Contract 的最小有效查看尺寸；Layout 与真实素材方向明显冲突；图片承担识别或证明任务却被压成缩略图。
- Map 虽记录 `4:3` 等比例，但实际构图没有给予媒体相应面积或同屏数量导致图片不可辨认。

先回写 Architecture Map，然后停止继续生图并向用户说明受影响 Section、可保留部分与修正建议。结构可以由确认后的文字方案解决；不强制为每个结构修正补图。用户确认方案后可直接进入 HTML；只有需要看图时才生成对应 Section Correction；只有该 Section 无法脱离相邻上下文判断时，才经用户明确同意重生原 Segment。不得自动重生整段或无提示增加候选。

### B. 记录为 HTML Correction Notes

- 图片比例方向正确但不精确；
- 字号、留白、标题换行、卡片尺寸或 CTA 位置需要微调；
- 真实文案和素材替换后才能准确判断的局部空间；
- CSS 可明确控制的圆角、边框、阴影和对齐。

不重新生图；在进入 HTML 时显式修正。

### C. 可接受的生图噪声

- 生成文字错误或局部对齐不精确；
- `4:3` 接近 `3:2` 或 `5:4`，但仍保持正常横向构图；
- 明确标记的占位图细节与真实企业不完全一致；
- 不影响模块任务、证据、主次和页面节奏判断的轻微偏差。

错换整个 Section、改变条目类型或数量、把未验证主张画成可信证据，不属于文字噪声，必须判为 A 类 Structure Failure。失败图片可以保留为视觉语言参考，但不得列入最终结构输入。

方向、构图、证据可见性和整页节奏已足以指导 HTML，且 A 类问题已消除时立即停止生图。

## 回归案例：Factory 并列证据

输入：Factory 模块包含车间全景、铜带线、管棒线、检测设备和仓储五张图，业务上没有指定其中一项更重要。

错误：固定一张 `16:9` 大图，其余四张作为永久小缩略图。这擅自制造了证据主次，也让四张设备图失去查看价值。

正确：先将内容关系记为“并列、等权证据”。可使用等权 Grid、Carousel 或 Viewer。Viewer 可以一次放大一项，但每一项都必须可切换到相同查看尺寸，并显示名称和必要说明。默认 Active Item 不等于业务优先级。
