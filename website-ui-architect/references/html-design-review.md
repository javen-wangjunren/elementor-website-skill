# HTML Design Review

用于 HTML First Draft 生成后、Browser / Implementation QA 之前的设计师视角审查。它判断渲染后的设计在真实内容与页面上下文中是否成立，不检查 DOM、浏览器兼容或平台实现。

## 基本边界

- 视觉方向稿是可验证的构图假设，不是 HTML 必须逐像素复制的答案。
- 方向稿阶段应已拦截模块任务、证据关系、优先级和上下文等 A 类结构问题；HTML Design Review 仍要基于真实渲染复核，但不应成为第一次思考模块逻辑的环节。
- 生成 HTML First Draft 时先执行 Visual Direction Review 留下的 `HTML Correction Notes`，不将已知的生图偏差机械复制到 HTML。
- 保留用户已确认的核心气质、信息层级与主要构图；修正生图偏差、意外空白、真实文案不适配和相邻 Section 冲突。
- 不因为一个历史失败案例禁止某类模块；判断必须结合当前内容、上下文与整页节奏。

## 视觉证据

1. 用户已提供当前 HTML 截图时，先基于该真实渲染证据审查。
2. 否则使用 Ego Browser 查看整页、当前 Section 及前后相邻区域；同时确认桌面与移动端的信息层级。
3. 浏览器不可用时才退回静态 HTML/CSS 检查，并说明视觉判断受限。

不为了仪式制作大量截图。整页视图加当前与相邻 Section 视图通常足够。

## 模糊反馈诊断

用户在调整 HTML 设计稿时，可能只能表达“怪怪的”、“很挤”、“很空”、“很 Low”或“不协调”等主观感受。不得要求用户先将其改写成专业设计术语，也不得因反馈模糊而直接重做整个模块。

先基于当前真实渲染、模块任务与前后 Section，将感受诊断为 1–3 个可验证的原因：

| 用户感受 | 优先检查 |
| --- | --- |
| 很挤 | 信息是否过多、间距层级是否不足、媒体比例是否占据过多空间 |
| 很空 | 内容是否不足以支撑当前面积、平均分栏是否制造无意义留白 |
| 很乱 | 是否存在多焦点竞争、对齐关系不清、元素类型或强调手段过多 |
| 很 Low | 证据或素材是否不足、组件比例是否失衡、装饰是否在替代真实内容 |
| 不协调 | 当前区域的 Surface、密度、媒体、强调色或视觉重量是否与相邻模块冲突 |
| 看不出重点 | 标题、数据、图片和 CTA 是否同时使用最高强调级别 |
| AI 感很重 | 是否存在套模板、卡片滥用、抽象文案、虚假证据或无意义装饰 |
| 颜色怪 | 颜色角色是否误用、强调色是否竞争、对比是否破坏层级或违反 Design System |
| 布局怪 | 真实信息的数量、长度、类型与当前 Layout 几何是否匹配 |
| 字体不舒服 | 字号、字重、行高、行宽、换行与层级关系是否合理 |

诊断流程：

```text
读取用户选中的模块和模糊感受
→ 查看当前渲染及前后上下文
→ 归纳 1–3 个最可能原因
→ 给出一个推荐调整方案及理由
→ 用户确认后再修改
```

- 诊断应优先找最早的结构原因，不默认用换色、加卡片、加阴影或动效处理。
- 原因明确且只有一个合理解时，只提供一个推荐方案；真正存在多个合理方向时，才简要比较最多 2–3 个选择。
- 不跟随模糊反馈静默更改已确认的内容任务、业务事实、Design System 或主要构图。
- 这一步是 HTML Design Review 内的沟通与定位机制，不新增交付物、评分表或独立流程。

## 审查粒度

通用的 Section Job、证据、信息几何、视觉重量和上下文标准以 [Module Design Review](module-design-review.md) 为唯一来源。HTML 阶段使用真实渲染在三个粒度复核：

### Section Job

- 模块是否快速回答内容框架规定的问题。
- 标题、核心证据与 CTA 是否一眼可见。
- Layout 是否服务内容关系，而非为了还原方向图而保留不再有效的形式。

### Section + Neighbors

- 同时查看前一个和后一个 Section，不孤立审查。
- 查找 Logo、KPI、CTA、卡片、大图、双栏或相同 Surface 的连续堆叠。
- 检查局部调整是否使相邻模块失去节奏、重复证明同一件事，或竞争同一视觉焦点。

### Full Page

- 页面顺序是否继续符合访客的理解与决策过程。
- 大图、文字、列表、数据、开放网格和文件证据是否形成必要的节奏变化。
- 视觉重点是否与模块在购买决策中的价值匹配。

## 问题分类与动作

### A. 明确设计问题

默认自动修正，整个 HTML First Draft 最多一轮：

- 前后模块明显重复 Logo、KPI、CTA 或主要结构；
- 短内容被机械分栏，产生大片无意义空白；
- 模块高度、信息密度或视觉重量明显失衡；
- 证据与对应主张失去上下文；
- 机械还原导致真实文案拥挤、空洞或不可扫读；
- 局部调整明显破坏整页节奏。

修正后必须重新查看受影响 Section 与相邻区域，不得因为局部变好而引入新的整页问题。

### B. 主观方向选择

停止自动调整，向用户说明“问题 → 建议 → 原因 → 影响”：

- 多个 Layout 都能完成任务；
- 需要改变已确认的品牌气质或主构图；
- 需要删除用户明确要求的内容或业务证据；
- 修正会实质改变页面任务、Section 顺序或转化策略。

### C. Browser / Implementation 问题

交给后续 QA：溢出、断点、资源加载、DOM 语义、键盘、Focus、真实交互、reduced motion 和浏览器兼容。

## 输出与停止条件

- Review 是内部步骤，不默认创建评分表或独立报告。
- 没有明确问题时，只说明“已完成 HTML 设计审查”。
- 已自动修正时，只说明影响用户判断的主要问题与修正结果。
- 修正后只剩局部审美偏好或多种合理方向时，交给用户，不持续自我重设。
- 用户已明确接受当前模块时，不为追求“更完美”重新打开设计门禁。
- 真实素材替换后出现新的构图或密度问题时，可对受影响 Section 重新执行一次局部 Review。
