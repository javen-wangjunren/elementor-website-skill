# 🧩 Elementor Site Skills

> 一套面向真实企业对企业（B2B）项目的分层建站工作流：先核实公司资料、规划页面、视觉风格与必要的克制动效，再完成浏览器验证和可维护的 Elementor 自定义组件。

这不是“输入一句话直接生成网站”的模板包，而是 **1 个总控 + 8 个专项 AI 工作角色（Skills）**。它会根据项目现状选择当前真正需要的阶段，并把业务判断、视觉确认和工程验证放在各自正确的位置。

## 🚀 从本地工作区到 WordPress

这不是一个下载后即可安装的通用组件包，而是一支为**当前网站项目**服务的 AI 建站队伍。它先在本地把内容和设计想清楚、把页面做成可浏览的样板，再将确认模块制作为可安装的 WordPress 插件。

最简单的使用路径是：

1. 下载或克隆这个仓库，将根目录下的 9 个 Skill 文件夹复制到 `~/.agents/skills/elementor/`。
2. 新建一个本地项目工作区，例如 `my-b2b-site/`；它不需要是 WordPress 根目录。
3. 调用 `elementor-site-team-manager`，告诉它公司资料、计划页面和目标；它会像项目经理一样判断现在该补资料、看参考、定页面、做设计，还是进入开发。
4. 第一次制作自定义组件时，`elementor-site-initialize` 会在确认路径创建插件骨架；进入 Elementor 前，流程还会按需整理全站颜色、字体和间距应该如何继承。
5. Widget 完成并在本地验证后，将**完整插件目录**复制到 WordPress 的 `wp-content/plugins/`，或把该插件目录压缩成 ZIP，在 WordPress 后台的“插件 → 安装插件 → 上传插件”中上传并启用。

> 只压缩生成的插件目录，不要把整个项目工作区、设计稿或 `docs/` 一起打包上传。使用前请确保目标 WordPress 已安装 Elementor。

你可以直接这样开始：

```text
使用 elementor-site-team-manager，帮助我从当前项目状态开始完成一个 B2B 企业站。

公司资料位于：<path>
计划页面：<pages>
项目工作区：<local-project-path>
目标：完成页面设计，并将确认模块实现为可维护的 Elementor 自定义 Widget 插件。
```

## 🎯 项目定位

这套 Skills 面向希望用 Elementor 建设专业企业官网的运营、设计师和外贸团队。它不是固定 Widget 模板，也不替代专业设计师，而是把真实 B2B 项目中依赖个人经验的内容、设计、开发和验证流程标准化。

- **普通外贸团队**：借助资料核验、页面大纲、视觉规范、设计审查和真实验证，稳定完成一个合格、可信、可转化、可维护的网站；
- **专业设计师**：可以在制定全站视觉规范、确认页面效果和审核品牌页面时接入，集中打磨首屏、主视觉、字体与动效。

如果用分数作比喻：流程负责把设计与实现下限稳定在 **70–80 分**，专业设计师负责把视觉和品牌上限推向 **90 分以上**。这只是能力定位，不是统一评分或效果承诺。

## ✨ 它解决什么

- 基于真实业务、证据和客户决策路径规划页面，不虚构能力、客户或案例；
- 在需要时研究 3–5 个确认案例，只借鉴方法，不复制品牌和素材；
- 先确认页面讲什么、长什么样、每个模块如何排列，再进入开发；
- 动效默认保持克制：先判断是否帮助理解、反馈或品牌表达，再决定是否加入，不为“显得高级”机械地让全页淡入；
- 把全站视觉规范转成 Elementor 可以继承的颜色、字体和间距规则，再把确认页面做成只开放必要编辑项的组件；
- 像工程返修一样按原因处理问题：内容不对改内容，整体风格不对改视觉规范，布局不对改页面设计，显示异常才改代码。

## 🏢 为什么从 B2B 出发

B2B 网站面对更复杂的业务信息和更长的决策链路。“设计好”不仅是好看，还要让客户看懂你做什么、相信你能做到，并愿意询价。因此，页面顺序、模块任务、真实证据和视觉重量都必须服务于客户决策。

最终示例使用 **WordPress + Elementor**，但页面规划、视觉规范、设计审查和按原因返工的方法，同样可以迁移到 Gutenberg、ACF、Next.js、Astro、React 或其他 CMS。原则始终是：**先把判断做对，再选择实现方式。**

AI 可以快速生成完整页面，也可能把未经确认的判断一路带进代码。这套分层流程的目的，就是在事实、内容、视觉系统、页面设计和实现之间建立清晰权威，让高成本错误更早暴露、更小范围修正。

## ✨ 动效是画龙点睛，不是完成条件

B2B 网站没有动效也应该完整、清晰、可信。默认只提供按钮、链接和状态切换等基础反馈；当内容确有层级或叙事价值时，才加入少量进入视口显现。滚动联动、Sticky 场景或多阶段动画属于少见的品牌级增强，通常只在首页、品牌型 About Us、活动页或需要解释复杂过程的核心页面中评估，而且每个重点页面最多一个。

- **Layer 1 / 基础反馈**：按钮、链接、菜单、Tabs、Accordion 等交互状态，默认使用 CSS 和少量原生 JavaScript；
- **Layer 2 / 内容显现**：只用于有层级或顺序价值的内容，默认使用 CSS、IntersectionObserver 或按需 WAAPI；
- **Layer 3 / 品牌级场景**：先单独重构并确认模块，再决定原生实现是否足够；只有复杂时间轴或滚动联动确有必要时，才按需评估 GSAP。

所有核心内容在无 JavaScript 和减少动态效果模式下仍然可见。普通模块不会增加运行库字段，也不会自动加载 GSAP、Motion 或其他第三方动画依赖。

如果已有页面看起来偏静态，可以这样开始：

```text
请分析这个已确认的 HTML 页面，看看哪些模块适合增加 B2B 动效。
先不要修改代码，只给我动效建议，并说明每个建议属于 Layer 1、Layer 2 还是 Layer 3、为什么需要。
```

可以把整套流程想成盖房子：先查清地基和需求，再画图、看效果、做样板，最后才正式施工。总控不会要求所有任务都从第一步开始；它会根据已有成果，从当前真正需要的位置继续。

```text
核实公司资料与真实素材
→ 必要时考察 3–5 个参考网站
→ 写清页面大纲：讲什么、先讲什么、拿什么证明
→ 定好全站装修规范：颜色、字体、间距、视觉气质与基础运动性格
→ 画页面施工图，确认每个模块的位置、任务和必要的动效意图
→ 查看并确认页面效果图
→ 制作可以真实浏览的 HTML 样板间
→ 一次施工一个 Elementor 组件
→ 在真实 Elementor 页面中组装并验收
```

## 🧭 这支 AI 建站队伍如何分工

你不需要先记住下面这些名称。把它们看成一支施工队即可：总控负责判断进度，专项 Skill 各自完成一类工作。

| Skill | 像什么角色 | 用通俗的话说 |
| --- | --- | --- |
| `elementor-site-team-manager` | 总包项目经理 | 看清当前进度，把任务交给正确的专项 Skill |
| `elementor-site-initialize` | 工地管理员 | 建好项目目录和插件骨架 |
| `website-reference-researcher` | 案例考察员 | 研究值得借鉴的网站，学方法但不照搬 |
| `website-page-content-architect` | 页面策划 | 写清页面给谁看、讲什么、按什么顺序讲 |
| `website-design-system-architect` | 装修规范设计师 | 定好全站共用的颜色、字体、间距、视觉气质与基础运动性格 |
| `elementor-site-style-adapter` | 规范翻译员 | 把视觉规范转成 Elementor 可继承的全站样式说明 |
| `website-ui-architect` | 页面设计师 | 画页面施工图和效果图，安排模块如何表达，并判断哪里值得加入动效 |
| `website-html-prototyper` | 样板间施工队 | 把确认设计与动效做成可真实浏览、可检查的交互 HTML 页面 |
| `elementor-widget-pipeline` | 组件施工队 | 把确认模块做成可编辑、可维护的 Elementor 组件 |

> 总控还会在资料不足时先做一次轻量的“公司资料核验”（Company Intake）。参考研究也只在确有需要时启动，不会让每个页面都走一遍完整流程。

## 🛡️ 这套流程会特别守住的几件事

- **事实先于设计**：没有依据时规划素材缺口，不编造认证、客户、产能或案例；
- **内容与视觉分别确认**：先定页面讲什么，再定全站长什么样；
- **施工图先于效果图**：先检查模块任务、证据关系和页面顺序，再生成视觉方向；
- **方向稿服务决策**：确认构图、主次、密度与节奏后，精确换行、间距和裁切交给 HTML；
- **动效必须有目的**：基础反馈保持轻量，内容显现按需使用，品牌级场景先单独确认；
- **该自动修正的自动修正，该由人决定的停下来**：实现问题由对应 Skill 修正，业务取舍和品牌方向由用户确认。

## 🛣️ 浏览器样板间，可以有两种施工方式

HTML 页面就像正式装修前的样板间：它能在真实浏览器中检查电脑和手机效果，也为后续 Elementor 组件提供施工依据。

### 整页优先

如果方向已经成熟、模块关系也清楚，或者你想尽快看到完整页面，可以先搭完整的 HTML 页面样板，再把其中边界清楚的模块做成 Elementor 组件。

### 逐模块优先

如果页面比较复杂，或某些模块需要反复打磨和跨页面复用，可以先逐个制作模块样板，确认后再拼成整页。

两条路可以切换；开始制作 Elementor 组件前，只需确认以哪一版页面样板为准。

## ✅ 每一步先确认什么

| 走到哪里 | 需要你确认什么 |
| --- | --- |
| 核实公司资料 | 公司做什么、服务谁、哪些主张和素材可以公开使用 |
| 研究参考网站 | 看哪些网站；只学规律，不复制品牌和内容 |
| 规划页面大纲 | 页面目标、内容顺序、真实文案和所需素材 |
| 制定全站装修规范 | 颜色、字体、间距、整体视觉气质与基础运动性格 |
| 绘制页面施工图 | 每个模块放在哪里、承担什么任务，以及是否真的需要动效 |
| 查看页面效果图 | 构图、内容主次、密度和整体节奏 |
| 检查浏览器样板间 | 电脑和手机上的真实页面是否符合预期 |
| 制作 Elementor 组件 | 哪些内容需要在后台编辑，以及最终以哪版设计为准 |

## 📁 过程中会沉淀下来的文件

这些文件相当于项目的资料册、施工图和验收记录，主要由总控维护。初次使用时不用逐个理解，只需知道重要决定会被保存，后续可以接着做，而不是每次从头开始。

```text
docs/
├── company/about-company.md
├── research/<scope>-visual-reference-brief.md
├── page-content/<page-slug>.md
├── design-system/design-system.md
├── elementor/elementor-style-contract.md
└── workflow-status.md

elementor-project.json

设计稿/
├── design-system/style-board.html
├── directions/<page-slug>/
├── pages/<page-slug>.html
└── modules/<module-slug>.html

<用户确认的插件路径>/
└── <plugin-slug>/                 # 最终复制或压缩后上传到 WordPress
```

Elementor 插件可以把所有组件放在同一层（`Flat`），也可以按业务分类管理（`Grouped`）。`elementor-site-initialize` 会根据组件数量提出建议；确认后，后续实现不会擅自改变结构。

## 🚧 这套 Skills 暂时不替你做的事

- 不替你安装 Elementor、搭建 WordPress 环境，或自动寻找站点根目录；
- 不把主题开发、线上发布和缓存清理混进组件制作流程；
- 不用生成图冒充真实工厂、设备、客户、证书或案例；
- 不会默认把颜色、字体、间距、圆角和动画全部开放为后台编辑项；
- 不会因为整页样板已经完成，就一次性批量生成所有组件；
- 不会把参考网站的品牌、素材或业务事实直接复制进你的项目；
- 不会直接改动 Elementor 后台的全站颜色、字体和间距；对应 Skill 只会先生成一份本地设置说明；
- 最终页面仍需要你在真实 Elementor 环境中组装并验收。
