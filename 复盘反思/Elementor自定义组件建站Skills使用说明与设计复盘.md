# Elementor 自定义组件建站 Skills：使用说明与设计复盘

## 写在前面

这套 Skills 不是一组互不相关的提示词，也不是一条从头跑到尾、越自动越好的流水线。它更像一支由总控协调的虚拟建站团队：先确认事实和页面任务，再建立视觉语言，随后设计页面，最后把已经确认的设计稳定地实现为 Elementor Widget。

它真正解决的问题不是“让 AI 会写一个 Elementor 组件”，而是：

> 如何让 AI 在不虚构业务、不跳过设计判断、不擅自改变确认稿的前提下，持续交付一套可审核、可恢复、可实现的网站设计。

Widget 的 PHP、CSS 和字段接线相对明确。最难的部分始终是设计，因为设计不是一次生成，而是一连串互相制约的判断：页面讲什么、为什么这样讲、用什么证据、采用什么构图、放进整页后是否协调、真实内容进入 HTML 后是否仍然成立。

因此，这套体系的核心不是“生成”，而是 **分层决策、证据约束、阶段自检、用户门禁和逐层收口**。AI 的第一次输出默认只是候选；每个关键阶段都必须先由 AI 自查，再由人在真正影响方向的位置把关。因为设计是一环扣一环的，上游错误如果没有及时拦截，后续往往只会被更精细地实现。

## 一、整套体系由什么组成

总控 `elementor-site-team-manager` 协调八个专项 Skill，并承担一个轻量的 Company Intake。它们不是一条每次都全量执行的流水线，而是按项目证据与不确定性条件路由：

| 角色 | Skill | 核心问题 | 主要产物 |
| --- | --- | --- | --- |
| 项目经理 / 路由总控 | `elementor-site-team-manager` | 现在处于哪个阶段，下一步该由谁做？ | 路由、门禁、`docs/workflow-status.md` |
| 业务资料整理 | 总控内置 Company Intake | 我们到底能说什么，有什么证据和素材？ | `docs/company/about-company.md` |
| 工程初始化 | `elementor-site-initialize` | Widget 应放进什么插件结构？ | `elementor-project.json`、插件骨架、交接目录 |
| 参考研究 | `website-reference-researcher` | 哪些跨行业案例值得借鉴，能迁移什么？ | Visual Reference Brief |
| 内容架构 | `website-page-content-architect` | 页面要完成什么决策任务，按什么顺序说？ | UI-ready Page Content Framework |
| 视觉系统 | `website-design-system-architect` | 整个网站应该使用什么视觉语言？ | Design Board、Design System |
| 样式适配 | `elementor-site-style-adapter` | 已确认的视觉系统如何落到 Elementor / 主题边界？ | 平台样式适配规则 |
| 页面与模块设计 | `website-ui-architect` | 每个 Section 怎么表达，设计假设和整页组合是否成立？ | UI Architecture Map、方向稿、Correction Notes、Module Slug |
| HTML 原型与视觉 QA | `website-html-prototyper` | 真实渲染后设计是否成立？ | 确认版 HTML、HTML Design Review、Browser QA |
| Elementor 实现 | `elementor-widget-pipeline` | 哪些内容可编辑，如何忠实实现为 Widget？ | 字段卡、PHP、CSS、可选 JS、验证结果 |

用户通常只需要调用总控，不需要记住所有专项 Skill。总控根据目标和已有证据选择当前唯一需要的专项能力；一个阶段确认后，再继续计算下一步，而不是一次加载全部规则。

这项设计很重要：它既降低用户的使用门槛，也避免 AI 同时扮演内容策划、视觉设计师和开发者时职责混乱。

## 二、每个 Skill 具体做什么

### 1. `elementor-site-team-manager`：总控与守门人

总控不直接替专项 Skill 做设计或写代码。它负责理解用户真正想完成的目标，检查最少的项目证据，判断缺少哪项依赖，并持续把任务交给正确阶段。

它的主要功能包括：

- 从新项目启动、单模块设计、已有 HTML 实现或中断恢复等不同入口开始工作；
- 在公司事实不足时执行轻量 Company Intake；
- 维护唯一的内部状态文件，记录已确认、待确认、当前门禁与下一步；
- 跨阶段只传递目标、确认输入、约束、产物和风险，防止上下文污染；
- 保留用户确认权，不把“文件已经存在”误判为“用户已经确认”；
- 识别发布、旧 Widget 排错、主题开发和 WordPress 环境管理等范围外任务。

它的亮点不是“管理步骤”，而是 **管理决策状态**。同一份 HTML、Design Board 或内容文档可能只是候选，也可能已经确认；如果没有可靠确认依据，总控不会擅自向下游传递。

### 2. Company Intake：共享事实底座

Company Intake 只在内容规划或新站视觉方向缺少可靠公司资料时触发。它一次只问少量会阻塞当前目标的问题，整理公司、产品、客户、能力、证据、素材与转化信息。

它会区分：

- `Verified`：有文件、证书、页面、数据或明确确认支持；
- `User-provided`：用户提供，但当前没有外部材料验证；
- `Pending`：仍然缺失或冲突；
- `Restricted Claim`：不应公开使用或证据不足的主张。

这个前置步骤看似简单，却是防止 AI 虚构案例、认证、交期、客户数量和制造能力的第一道防线。它不是品牌咨询，不替用户发明定位，也不会提前规划页面 Section。

### 3. `elementor-site-initialize`：搭好工程容器

初始化 Skill 在第一个自定义 Widget 之前使用。它根据预计 Widget 数量和业务复杂度，推荐并让用户确认插件采用 `Flat` 或 `Grouped` 结构。

- `Flat` 适合约 1–20 个 Widget、单一业务范围和短中期项目；
- `Grouped` 适合 21 个以上 Widget、长期纯 Elementor 网站或多个稳定业务家族。

确认后，它建立项目配置、插件骨架、设计交接目录，以及在存在主题证据时生成只读扫描摘要。它不安装 Elementor、不寻找 WordPress 根目录、不修改主题，也不趁初始化创建示例 Widget。

亮点在于 **按未来规模选架构，但只创建最小骨架**。结构一旦确认，后续新增一个 Widget 不会偷偷迁移目录或引入第二套注册器。

### 4. `website-page-content-architect`：先把页面讲清楚

这个 Skill 在视觉设计之前工作。它把真实业务资料转化为可直接排版的页面内容框架，回答：页面服务谁、承担什么任务、访客按什么顺序形成判断、每个 Section 应说什么、需要什么证据、CTA 应该出现在哪里。

它支持三种模式：新页面、现有页面审查和页面族规划。默认产物不是冗长策略报告，而是一份简短的 UI-ready 内容框架，包含真实长度的标题、描述、列表、CTA 和素材要求。

它最关键的设计是：

- 用“访客决策问题”组织页面，而不是先套 Hero、卡片、Logo 墙等组件；
- 每个 Section 只承担一个主要决策任务；
- 把模块标记为 `Core / Recommended / Optional`，不因素材暂缺就删除有价值的证据模块；
- 允许规划案例、认证或客户证据，但在没有真实内容时绝不编造访客可见文案；
- 交付前执行一次内容架构自查，修正顺序、重复、缺口和可扫读性问题。

它不决定布局，不写 HTML，也不生成 Canonical Module Slug。内容的职责先确定，视觉形式留给后续设计。

### 5. `website-reference-researcher`：把参考网站变成可迁移证据

它不是静态“品牌网站收藏夹”，也不负责复制别人的 Design System。只有同行参考不足、目标需要更强的品牌或体验表达、页面缺少中心叙事、视觉方向持续模板化、关键模块没有合适表达，或用户明确给出参考网站时，才触发研究。

它会先按“设计问题相似性”而不是行业标签选择 3–5 个真实网站：通常包括同行、相邻行业、品牌叙事和专项模块参考。研究输出是一份 Visual Reference Brief，分别记录品牌叙事、页面架构、内容取舍、Art Direction、视觉系统，以及哪些是 `Observed / Inferred / Transferable / Not Transferable`。

下游只读取自己需要的字段：内容架构读取叙事与证据策略；视觉系统读取 Art Direction 与视觉边界；UI Architect 读取模块构图、媒体和响应式迁移原则。外站的事实、专属素材、品牌身份和完整风格都不能照搬进项目。

### 6. `website-design-system-architect`：建立全站视觉语言

这个 Skill 不设计某个页面，而是定义所有页面共享的视觉基线。新站从品牌、真实素材与适用的 Visual Reference Brief 开始；旧站则从真实页面中区分哪些视觉规则应该保留、统一、淘汰或继续观察。

标准生命周期是：

```text
公司与品牌输入 +（条件触发时）Visual Reference Brief
→ 2–3 个文字方向
→ 用户选定一个方向
→ 对话内形成临时规则草稿
→ 生成单方向 Design Board
→ 设计师自查并自动修正一轮
→ 用户确认
→ 写入 Active Baseline Design System
→ 再做一致性与可用性自查
```

这里刻意没有一开始就生成三套高保真网页。先比较文字方向，可以用很低成本判断气质、配色关系、字体倾向、页面密度和图片方式；用户选定后，只制作一个 Design Board 来验证颜色、字体、间距、形状和基础组件是否属于同一种语言。

Design Board 不是页面稿，也不是营销 Landing Page。它只验证 Button、Card、List、Tabs、Accordion、Table 等基础规则，不混入 Hero、Gallery、Header、Footer 或完整业务模块。用户确认 Board 后，才形成正式但可演进的 `Active Baseline`。

亮点是 **先规则、后组合验证、再正式固化**。正式系统还会把规则分成 `Locked / Flexible / Open`，避免 AI 把尚未验证的细节伪装成既定规范。

### 7. `website-ui-architect`：把内容和规则变成真正的页面

这是整套体系中最复杂的 Skill。它读取已确认的 Page Content Framework、Design System、真实素材，以及适用的 Visual Reference Brief，把“应该说什么”与“网站应该像什么”转化为具体构图、方向稿和可交给 HTML 原型阶段的实现决策。

完整页面必须先生成 Page UI Architecture Map。Map 会逐个 Section 规定：模块任务、访客只需记住什么、内容之间属于并列、主从、分类、过程还是对比、核心证据、证据的查看方式与优先级、推荐 Layout、媒体关系、图片比例、CTA 层级、Surface 衔接、移动端顺序和需要避免的重复形式。它不锁定像素和 DOM，但必须让下一步不再重新猜构图。

Map 交给用户确认前，先执行一次 **Module Design Review**，从四层判断每个模块是否成立：

1. **Commercial Job**：模块是否完成当前商业任务，视觉重量是否匹配业务重要性；
2. **Evidence Structure**：主张有没有适当、真实且足够可看的证据支持；
3. **Information Geometry**：Layout 是否匹配真实条目数量、长度、媒体方向和内容关系；
4. **Visual and Page Context**：与前后模块是否重复、争抢焦点或破坏整页节奏。

“方向图忠实还原了 Map”不等于设计合理。如果 Map 已把五项并列设备证据写成永久“一张大图、四张小图”，生图越忠实，后续 HTML 返工反而越确定。正确做法是先将其定义为等权证据；Viewer 可以一次放大一项，但每张图都必须能切换到相同查看尺寸，默认 Active Item 不代表业务优先级。

Map 通过审查并由用户确认后，才按需生成图片方向稿。长页面以 2–4 个 Section 为一组生成分段稿，用来判断真实密度、留白、构图、证据可见性和素材比例；整页 Composite Preview 只在用户明确需要时，基于已确认分段拼合。这样避免为了把十几个模块塞进一张长图而压扁 Section、缩小文字或把图片改成失真的横条。

方向稿是低成本设计假设，不是设计师终稿，也不是 HTML 的逐像素合同。它只需让人判断模块构图、证据主次、大致比例、密度、留白和节奏，不需要把接近 `4:3` 的横图反复生成为精确 `4:3`。精确比例、Section 高度、文字换行与最终裁切应在 HTML 中控制。

方向稿生成后再次执行 Module Design Review，并按返工成本分流：

- **A 类结构问题**：任务、证据关系、内容主次或上下文明显错误。回写 Map，只重生受影响分段一次；
- **B 类 HTML Correction Notes**：比例、字号、留白、换行、卡片尺寸等可由真实 HTML 明确修正的问题，不重新生图；
- **C 类生图噪声**：生成文字错误、轻微比例和对齐偏差，不影响方向判断，直接接受。

当 A 类问题已经消除，方向足以指导 HTML 时立即停止生图。Review 的目标是降低后续重写成本，不是把图片初稿打磨成最终设计文件。

方向确认后，UI Architect 将 Map、方向稿和 Correction Notes 交给 HTML Prototyper。它不再直接写 HTML，以免同一角色一边定义设计、一边在浏览器中为实现妥协而掩盖上游问题。

这个 Skill 还负责确定 Canonical Module Slug。Slug 同时约束设计稿 basename、Widget `get_name()` 和相关资源文件，从设计一直贯穿到代码，避免出现 `final-v2-new` 式版本漂移。

### 8. `website-html-prototyper`：用真实页面完成视觉 QA

HTML Prototyper 以确认的 UI Architecture Map、Design System、真实文案和真实素材为输入，生成或迭代 HTML First Draft，并在浏览器中完成 HTML Design Review 与 Browser QA。它验证的不是“图片像不像”，而是颜色在整页是否和谐、排版和留白是否成立、模块的真实内容密度是否合理、断点是否溢出、图片裁切与交互是否可靠。

它将问题回退到正确层：核心构图、证据关系和页面节奏回到 UI Architect；全站共享的配色、字体、Surface 或组件问题回到 Design System；公司事实和内容取舍回到 Page Content；仅属于尺寸、换行、裁切、断点或实现的内容留在 HTML 阶段修正。确认版 HTML 才是 Widget Pipeline 的实现源。

### 9. `elementor-site-style-adapter`：明确平台边界

Style Adapter 在进入 Elementor 实现前，将已确认的通用视觉系统映射为可执行的平台规则：哪些由 Widget CSS 承担，哪些必须遵守主题或 Elementor 的既有边界，避免 Pipeline 在实现时重新发明视觉语言。

### 10. `elementor-widget-pipeline`：克制地实现，而不是二次设计

Pipeline 一次只实现一个已经确认的 Section。它首先读取最终 HTML 实现源，然后提出一张最小字段确认卡，明确哪些内容允许用户在 Elementor 编辑，哪些布局和视觉规则固定在代码中。

用户确认字段前，Pipeline 不写 PHP、CSS 或 JS。默认不开放颜色、字体、间距、圆角、阴影、列数和动画等 Style Controls；数量稳定的内容也不会为了“以后也许有用”就使用 Repeater。

确认后，它才：

- 继承 Canonical Module Slug；
- 增量接入现有插件，不覆盖入口或重建注册器；
- 创建 Widget PHP、命名空间 CSS 和确有交互时的 JS；
- 对多实例、Elementor 编辑器重新渲染、键盘与 reduced motion 做相应处理；
- 完成 PHP、JS、资源路径、命名一致性和 CSS 隔离等静态检查；
- 给出需要用户在真实 Elementor 中完成的手动验证步骤。

它的亮点是 **把可编辑性当作需要克制的产品决策**。字段越多不代表 Widget 越强，反而可能让确认过的设计被后台随意破坏。

## 三、为什么设计必须拆成多个环节

最初很容易把设计理解成“给 AI 一份内容和几个参考，让它生成漂亮页面”。真实项目会很快暴露问题：单个模块看上去精致，但整个页面像模板拼接；卡片、双栏、数字带和双 CTA 高频重复；制造企业该有的产品、设备、工艺和质检证据被图标或空泛文案代替。

根本原因不是 AI 不会写 CSS，而是它在一次生成中同时做了太多未经确认的决定。

这套流程因此把设计拆成八个连续决策层：

```text
真实业务事实
→ 页面内容职责与决策顺序
→ 全站视觉语言
→ 页面构图、证据关系与媒体契约
→ Architecture Map Module Design Review
→ 图片方向验证与 A/B/C 分流
→ 真实 HTML Design Review
→ Browser / Implementation QA 与 Widget 实现
```

每一层只解决一种不确定性：

1. **事实层**解决“能不能这样说”；
2. **参考研究层（条件触发）**解决“外部案例中哪些原则可迁移”；
3. **内容层**解决“应该说什么、先说什么”；
4. **Design System 层**解决“整个网站使用什么视觉语言”；
5. **Architecture Map 层**解决“每个 Section 如何构图、证据如何查看、整页如何形成节奏”；
6. **Map Review 与方向稿层**在低成本阶段验证设计假设；
7. **HTML Review 层**用真实内容、真实浏览器和整页上下文验证“设计是否真正成立”；
8. **平台实现层**验证 Elementor 接线和可编辑性是否可靠。

这不是为了流程而流程。它的价值在于让昂贵的返工尽可能发生在更早、更便宜的阶段：方向不对，在文字方向阶段改；构图不对，在 Map 或方向稿阶段改；真实内容导致拥挤和空洞，在 HTML Review 阶段改；平台接线问题，最后才进入 Pipeline 处理。

## 四、如何确保设计质量

### 1. 不允许内容、视觉和实现互相越权

研究 Skill 不把外站事实变成项目事实；内容 Skill 不提前决定 Layout；Design System 不设计业务 Section；UI Architect 不发明公司事实；HTML Prototyper 不用 CSS 掩盖上游构图问题；Pipeline 不为了接字段而改变设计。职责边界使每个决定都能追溯到正确来源。

### 2. 不是一次 QA，而是四个不同的审查门

设计链路中存在四道不能混为一谈的检查：

| 审查 | 检查对象 | 重点 |
| --- | --- | --- |
| Architecture Map Module Design Review | Map 中的模块方案 | 商业任务、证据结构、信息几何、页面上下文 |
| Visual Direction Review | 图片方向稿 | Map Fidelity、设计假设、证据可见性、密度、节奏及 A/B/C 分流 |
| HTML Design Review | 真实渲染后的 HTML | Correction Notes、真实内容适配、相邻关系、视觉重量、整页节奏 |
| Browser / Implementation QA | 可运行 HTML | 响应式、溢出、资源、交互、键盘、Focus、reduced motion |

前两道审查共享同一套 Module Design Review 判断标准，区别是一次审查文字方案，一次审查方案视觉化后的结果。方向图不假装能验证 DOM 和响应式；HTML Design Review 不把浏览器兼容混进设计判断；实现 QA 也不擅自改变已确认的页面策略。

### 3. 每一阶段都采用“AI 自查 → 明确修正 → 人工门禁”

AI 一次性输出通常都会有问题，不能等到页面全部完成后才统一 QA。每个阶段的产物都要先回答：是否完成本阶段任务、是否把上游错误带入下游、是否出现明确可修正的问题。

AI 负责发现和修正有充分证据的问题；用户负责业务真实性、主观方向和多个合理方案之间的选择。这种双重把关不是重复劳动，而是适配“AI 生成速度快，但判断稳定性不足”的协作方式。

### 4. 既自动修正，也限制自动修正

每次设计审查只允许自动修正一轮有充分证据的明确问题。比如明显重复的 KPI、无意义空白、证据与主张脱节或真实文案被机械构图挤压，可以直接修正。

如果涉及品牌气质、多个合理 Layout、Section 顺序或业务内容取舍，必须停下来交给用户。这个“只修一轮”的限制很关键：它防止 AI 因为自己的连续微调不断推翻先前方向，也避免在审美不确定时陷入无止境生成。

### 5. 每个主观阶段都有用户门禁

文字方向、Design Board、内容框架、UI Architecture Map、视觉方向、最终 HTML 和 Elementor 字段，都在各自最合适的时点由用户确认。Reference Research 仅在触发时确认研究对象；其简报是证据输入，不额外增加最终决策门禁。文件存在只证明产物存在，不证明用户已确认。

门禁不是让用户审批每个内部检查表，而是让用户只决定那些 AI 无法替代的业务事实、审美偏好与编辑需求。内部 QA 可以严格，用户交互必须轻量。

### 6. 真实浏览器是设计证据的一部分

图片方向只是设计假设。HTML First Draft 完成后，要在真实渲染中同时看当前 Section、相邻 Section 和整页：一个 KPI 带单独看可能成立，放在带客户 Logo 的 Hero 之后就可能形成证据堆叠；一个三栏结构单独看整齐，装入短内容后可能制造大片空白。

设计质量最终取决于上下文，而不是孤立截图。

## 五、这套体系如何规避常见的“AI 味”

所谓“AI 味”通常不是某一种颜色、圆角或字体造成的，而是 **没有业务依据的平均化设计**：所有信息被处理成同等大小的卡片，所有页面使用相似 Hero，所有模块都追求独立精致，却没有真实证据和整体节奏。

这套 Skills 从多个位置同时拦截它。

### 1. 不从条目数量直接推导卡片网格

设计探索遵循：

```text
模块任务 → 核心信息 → 证据与素材 → 表达方式 → Layout
```

有三条内容不等于必须三张卡片。流程可能适合时间线，规格适合表格，工厂能力适合现场大图与尺度关系，证书适合真实文件展示。

### 2. 证据优先于装饰

B2B 和企业站设计会先问“这个模块要证明什么”。产品、设备、人员、过程、数据和文件应参与信息表达；图标、通用图库和生成图不能伪装真实企业证据。CTA 也尽量靠近足以支持行动的证据。

### 3. 用信息几何代替机械平均分栏

Layout 必须匹配真实信息的数量、长度和类型。短数字不应为了占满宽屏被做成巨大单元；内容少时，优先合并、嵌入上下文或使用自然宽度，而不是靠卡片、阴影和装饰填满空间。

模块形式还必须服从信息关系：并列证据不能无理由变成永久主次，辅助 CTA 不应获得核心证明模块的高度和对比度，产品与材料不能在需要视觉识别时只剩文字 List，证书也不能缩成无法阅读的装饰拼贴。判断一种 Layout 是否“好看”之前，先问它是否让当前最重要的信息更容易理解和验证。

### 4. 先删除和合并，再装饰

当模块与相邻内容重复时，优先判断它是否还应该独立存在，或是否应迁移到更有上下文的位置。不能只通过换背景、加阴影、换卡片样式来掩盖结构问题。

### 5. 控制整页节奏，而不是让每段都抢注意力

一个视区只保留一个主焦点。图片、标题、数字、Logo 和 CTA 不应同时使用最高强调级别。整页需要在大图、文字、列表、数据、开放网格和文件证据之间形成强弱变化，但也不能为了“不重复”把每个模块都做成新奇结构。

### 6. 长页面不压缩进一张生图

分段稿优先，避免 AI 为适应单张长画布而压扁模块、削弱留白、缩小文字和破坏正常素材比例。Composite Preview 仅用于用户需要整体浏览时，并且只能由确认分段拼合；精确比例和真实换行留给 HTML。

### 7. 设计判断由当前体系内部完成

当前流程不再依赖额外的通用设计顾问 Skill。Design System 的设计师自查负责视觉语言、基础组件和一致性；Module Design Review 负责商业任务、证据结构、信息几何和页面上下文；HTML Design Review 与 Browser QA 分别负责真实渲染和实现验证。这些规则已经覆盖实际项目需要，也更贴近 B2B 网站的业务与证据环境。

删除通用顾问并不代表降低审美要求，而是避免引入与当前任务重复、缺少项目上下文或带有绝对审美偏好的建议。需要新的设计方向时，应优先回到适用的 Visual Reference Brief、真实素材、Design System 和当前页面任务，而不是再叠加一层泛化评审。

最终要避免的不是某个具体组件，而是 **没有内容理由、没有证据理由、没有上下文理由的设计决定**。

## 六、如何使用整套 Skills

### 场景一：从零开始做一套网站

最简单的用法是只调用总控，并说明最终目标、公司资料位置、预期页面和是否需要自定义 Widget。总控通常会按实际缺口推进：

```text
Company Intake（资料不足时）
→ Reference Research（仅在同行参考不足、品牌/体验目标较高或用户提供参考时）
├→ Page Content
└→ Design System

Initialize（插件不存在时）

Page Content + Design System 均确认
→ UI Architecture Map
→ Map Module Design Review + 一轮明确修正
→ 用户确认 Map
→ 图片视觉方向（按需）
→ Visual Direction Review（A/B/C 分流）
→ 用户确认视觉方向
→ HTML Prototyper：执行 Correction Notes + HTML Design Review + Browser QA
→ 用户确认页面与当前 Widget 实现源
→ Style Adapter：确认平台样式边界
→ Pipeline 逐个实现 Widget
→ 用户在 Elementor 中组装并做最终整页验收
```

内容框架和 Design System 是完整页面 UI 的两个独立前置，在条件允许时可以分别推进；插件初始化则是 Widget 实现的前置，不是视觉设计的前置。

### 场景二：只做一个独立模块

如果已有明确的真实内容、页面上下文和确认版 Design System，不必先创建整页内容框架或 Architecture Map。可以由 UI Architect 完成模块方向与 Canonical Module Slug，再交给 HTML Prototyper 完成模块 HTML 与视觉 QA，最后进入 Pipeline。

### 场景三：已有确认版 HTML，只想实现 Widget

先确认插件是否存在。如果不存在，Initialize 创建骨架后立即返回 Pipeline；如果存在，则直接确认 Section 边界、Module Slug、最终 HTML 来源和最小字段卡。

### 场景四：中断后恢复

再次调用总控并说明继续当前项目。总控会结合 `docs/workflow-status.md`、现有产物和对话证据恢复阶段。文件只能证明“产物存在”，不能单独证明“用户已经确认”；确认依据不清楚时会停在对应门禁。

### 推荐的调用方式

可以直接这样表达：

> 使用 `elementor-site-team-manager`，继续完成这个企业站的首页设计和自定义 Widget。请根据当前项目状态判断下一步，不重做已经确认的内容；每到需要我决定的门禁时，给我简短说明和推荐意见。

用户不需要把所有步骤一次说全，也不需要手动切换各个专项 Skill。

## 七、使用时必须理解的边界

- 总控不会负责 Elementor 安装、WordPress 环境搭建或自动寻找站点根目录；
- 主题开发、`functions.php` 修改和全站字体注入不属于 Widget Pipeline；
- Pipeline 用于新增或迁移确认版 Widget，不用于旧 Widget 白屏、面板不可见或交互失效等故障排查；
- 上传、缓存清理和生产发布属于外围流程，可另用 Release SOP；
- Pipeline 的验证以静态检查和单 Widget 手动验证步骤收口，不会假装已经在用户的 Elementor 后台完成实际验证；
- 多个 Widget 仍需一个一个确认字段和实现，整页 HTML 不等于授权批量生成所有 Widget；
- 最终在 Elementor 中组装整页并对照确认版页面 HTML 做视觉验收，仍然是用户保留的人工门禁。

这些边界并不是能力缺口，而是为了避免一个 Skill 在缺少授权和环境证据时擅自扩大操作范围。

## 八、设计这套 Skills 的心路历程

最开始，最容易关注的是“如何把 HTML 变成 Elementor Widget”。但实践后会发现，代码层的问题往往最好定义：注册文件、字段、命名空间 CSS、多实例 JS 和检查清单都可以写成明确规则。真正反复返工的，是 HTML 之前的判断。

AI 很擅长快速给出一个看起来完整的页面，也正因为如此，它容易过早收敛：业务资料刚读完，就直接跳到熟悉的 Hero、数字带、卡片网格和 CTA；单个模块都有模有样，组合后却缺少真实企业特征。

继续补规则时，又出现了另一个风险：为了确保质量，把每个判断都做成文档、表格和用户门禁。流程会显得专业，却越来越难用。因此，这套 Skill 后来的重要调整，不只是“增加规则”，也包括主动删掉不必要的中间产物：

- 内部分析不默认全部展示；
- 临时 Design System 草稿只保留在对话中；
- 单模块 HTML 不再是所有路径的固定前置；
- 图片方向稿达到判断目的就停止，不追求生成图的像素精度；
- QA 严格执行，但只向用户报告真正影响判断的问题；
- 简单任务走短路径，复杂任务才启用完整链路。

首页实战进一步验证了这一点。早期从页面信息结构直接生成设计，虽然形式完整，却出现了大量通用卡片、无上下文数据和未经证实的服务表达。经过 Content、Design System、Architecture Map、方向稿、HTML 及逐模块 Review 后，最终首页不依赖炫技，也能形成可信、清楚、证据充分的 B2B 页面。

过程中暴露的典型问题也成为了可复用规则：

- Hero 已经承载客户 Logo 时，紧接独立 KPI 带容易形成信息堆叠；数据更适合进入有上下文的 Why Choose Us；
- 产品和材料需要真实或明确占位的产品图，不能只用抽象列表替代识别；
- 工厂与设备的多张图片属于并列证据时，应让每项获得同等查看机会；
- 证书和报告的价值在于可看、可识别，不能被做成过小装饰；
- 企业当前不提供的 Processing 服务必须删除，不能因为设计稿已经存在就继续实现。

这些修改并不说明方向稿必须做到完美，恰恰说明它只需提前拦住会导致 HTML 大幅重写的结构错误；其余细节应在更容易精确调整的 HTML 阶段处理。

随着规则增加，Skill 本身也需要避免臃肿。当前做法是让主 `SKILL.md` 只承担流程路由，把共享的模块判断统一放在 `Module Design Review`，Visual Direction 与 HTML Review 只保留各自阶段新增的规则。行为案例可以分组压缩，但关键回归行为不能丢失。无损瘦身的标准不是文件变短，而是规则有唯一来源、路径更清楚、原有能力仍可验证。

这个过程让我逐渐确认：

> 好的 Skill 不是把最佳实践写得越多越好，而是把最容易造成高成本返工的判断放在正确阶段，并让用户只参与真正需要人的决定。

从这个角度看，这套 Skills 也是把个人隐性经验显性化的过程。过去凭直觉知道什么时候不能继续、什么时候页面像模板、什么时候证据不够；现在必须把它们转换成 AI 能执行的输入标准、职责边界、优先级、门禁和停止条件。

## 九、这套体系当前最有价值的设计原则

1. **固定质量底线，不固定所有实现路径。** 事实、关键方向和字段确认不可跳过；整页优先或逐模块优先可以按项目选择。
2. **每个产物都必须有明确的下游消费者。** 没有人会使用的报告不默认创建。
3. **用户可见门禁与 AI 内部 QA 分开。** QA 可以细，交互要轻。
4. **文件存在不等于主观确认。** 状态必须有对话或明确输入作为依据。
5. **真实内容和上下文高于孤立的漂亮截图。** 页面设计最终要在真实 HTML 中成立。
6. **实现忠于设计，设计忠于内容，内容忠于事实。** 每一层都不能越权替上一层重新决定。
7. **停止条件和生成能力同样重要。** 达到当前阶段的判断目标后就停止，避免为了“更完整”持续制造变体和漂移。
8. **AI 首稿默认需要自检，人负责最终判断。** 每个阶段先完成内部 Review，再把真正影响方向的问题交给用户。
9. **Map Fidelity 不等于设计正确。** 在生图前先验证模块任务、证据关系、信息几何和页面上下文。
10. **方向稿追求可判断，不追求极致精确。** 它负责降低结构返工，不替代 HTML 中的真实设计验证。
11. **模块形式必须由业务作用和页面环境决定。** 辅助内容可以一带而过，核心证据必须可看；不能仅凭“单调”或“炫酷”评价模块好坏。

## 总结

这套 Elementor Skills 的表面产物是内容框架、Design System、HTML 和 Widget，真正沉淀下来的却是一套人与 AI 协作完成专业设计的机制：

```text
用事实限制幻觉
用职责限制越权
用阶段自检拦截错误传递
用门禁保护主观决定
用多层审查提高首次交付质量
用灵活路径控制流程成本
用明确交接减少实现漂移
```

Widget 实现确实是不可缺少的一环，但它不应该承担设计阶段没有解决的问题。只有前面的业务、内容、视觉系统和页面构图环环相扣，后面的 Elementor 开发才会变成一件相对清楚、稳定而简单的事情。

这也是整套 Skills 最核心的设计思想：**不期待 AI 一次做对，而是让每一阶段都先产出、再自检、再由人确认关键判断，使错误更难跨阶段传播，也更容易在低成本位置被及时纠正。**
