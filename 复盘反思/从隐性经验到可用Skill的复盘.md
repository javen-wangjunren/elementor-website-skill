# 从隐性经验到可用 Skill 的复盘

## 核心结论

这套 Skill 的真正价值，不是把建站工作变成一条越来越复杂的自动流水线，而是把过去依赖个人经验的判断，整理成 AI 能理解、用户能控制、项目能重复执行的协作方式。

最重要的原则是：

> Skill 应该明确“必须确认什么”，但不应把“必须怎么做”写死。

好的 Skill 既能守住质量底线，也允许根据项目成熟度、素材情况和用户习惯选择最短路径。

## 1. Skill 的本质是把隐性经验显性化

过去的工作流看起来很自然：先了解公司，再规划内容，参考同行，确定风格，设计页面，最后开发 Widget。真正执行时，其中包含了大量没有被写下来的判断：

- 什么信息不足以开始设计；
- 什么事实不能由 AI 编造；
- 什么页面需要先看整体图片方向；
- 什么模块适合单独打磨；
- 什么时候可以直接生成整页 HTML；
- 什么必须由用户确认后才能继续；
- 什么属于 AI 内部 QA，不需要增加用户负担。

设计 Skill 的过程，就是把这些判断从“我平时就是这样做的”，转化成清晰的输入、产物、门禁、路由和 QA。

因此，Skill 建设也是对自身工作方法的一次反向梳理。很多原本凭感觉完成的工作，只有尝试教给 AI 时，才会发现其中缺少明确标准。

## 2. 最大风险是为了流程而流程

在持续补充规则时，很容易出现本末倒置：

- 为每个中间判断创建一份文档；
- 为了形式完整，要求所有项目从第一阶段重新开始；
- 把 AI 内部检查表全部暴露给用户；
- 将推荐路径写成强制路径；
- 花大量时间优化 Skill，却没有继续交付真实网站。

这会让流程看起来专业，但实际使用成本越来越高，甚至偏离原本更直接、有效的人工工作流。

判断一条规则是否值得保留，可以问三个问题：

1. 它能否减少真实项目中的高频错误？
2. 它是否会影响下游质量或返工成本？
3. 它是否真的需要用户参与，而不是由 AI 内部检查？

如果三个答案都是否定的，这条规则通常不应该成为固定步骤。

## 3. 门禁要稳定，实现路径要灵活

必须稳定的是关键质量门禁，例如：

- 公司事实是否足够、是否经过确认；
- Page Content 是否能直接支持 UI 设计；
- Design System 和视觉方向是否确认；
- 当前 Widget 的最终设计源和字段是否确认；
- 最终页面是否经过人工验收。

可以灵活的是达到这些结果的方式，例如：

- Company Intake 可以服务 Page Content，也可以服务 Design System；
- 可以先生成整页图片方向稿，也可以在方向明确时直接写 HTML；
- 可以直接完成整页 HTML，也可以逐模块设计后拼接；
- Pipeline 可以读取独立模块 HTML，也可以读取整页 HTML 中边界明确的 Section；
- 简单任务可以跳过不必要的中间产物。

这形成了一种更合适的 Skill 设计方式：

```text
固定输入底线
→ 固定确认门禁
→ 中间路径按项目选择
→ 固定交付质量
```

## 4. 用户可见流程与 AI 内部 QA 要分开

很多检查是必要的，但不应该全部变成用户要阅读和确认的表格。

用户通常只需要确认：

- 方向是否正确；
- 内容和事实是否正确；
- 设计稿是否满意；
- Widget 字段是否符合编辑需求。

AI 内部则应自行检查：

- 模块是否完成信息任务；
- 重点、证据、媒体和 CTA 层级是否合理；
- 是否滥用卡片或通用模板；
- 页面节奏和模块关系是否协调；
- 移动端、长文本和基础可访问性是否成立。

原则是：

> QA 可以严格，但交互必须轻量。

只有发现阻塞、风险或必须修改的问题时，才需要向用户展开说明。

## 5. Skill 应贴合真实工作流，而不是理想化流程

稳定的 Skill 不应来自一次性理论设计，而应来自真实项目中的反复验证：

```text
先按现有习惯完成真实任务
→ 记录 AI 出错或误解的位置
→ 找到造成返工的高杠杆问题
→ 增加最小规则或门禁
→ 再用真实任务验证
```

本次实践中，真正值得修正的问题往往很具体：

- Intake 被错误地固定路由到内容阶段；
- 整页快速设计可能跳过逐 Section 的模块思考；
- 单模块 HTML 被误认为所有路径的固定产物；
- 人工整页验收被误判成流程缺口。

这些调整比继续扩充抽象框架更有价值，因为它们直接减少误路由、重复工作和错误实现。

## 6. 评价 Skill 的标准不是“完整”，而是“好用”

一套 Skill 是否成熟，可以用以下标准判断：

- 新任务能否快速进入正确阶段；
- AI 是否知道开始工作前缺少什么；
- 用户是否只需要做真正重要的确认；
- 简单项目能否走短路径；
- 复杂项目能否切换到稳妥路径；
- 中断后是否能够恢复上下文；
- 输出能否直接交给下游使用；
- 是否比没有 Skill 时减少返工；
- Skill 的维护成本是否低于它节省的成本。

如果 Skill 越来越完整，却让日常工作越来越慢，它就需要删减，而不是继续增加规则。

## 7. 对后续 Skill 优化的约束

后续继续优化这套体系时，应坚持：

1. 先解决真实项目中出现的问题，不为假设场景提前扩建。
2. 优先修改高杠杆路由、门禁和交接，少增加中间文档。
3. 推荐一种默认路径，但保留经过确认的替代路径。
4. 不把内部 QA 转化成用户必须填写的流程表。
5. 每个产物必须有明确下游消费者，否则不默认创建。
6. 定期删除已经失效、重复或与真实工作流冲突的规则。
7. Skill 优化应服务于网站交付，而不是成为独立于交付的长期工程。

## 总结

构建这套 Skill 最有价值的收获，是逐渐理解了怎样让 AI 参与专业工作：不是要求 AI 一次性替代设计师，而是把关键判断、事实边界和质量门禁交代清楚，再给它足够的执行弹性。

这项工作确实有难度，因为它同时要求理解业务、设计、开发、协作和流程工程。但最终目标仍然很朴素：让 AI 更稳定地复现已经被实践证明有效的工作方式，减少返工，持续交付达到商业目标的网站。
