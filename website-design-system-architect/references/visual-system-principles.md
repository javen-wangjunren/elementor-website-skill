# Visual System Principles

用于形成临时规则草稿、生成单方向 Design Board，以及审查 Active Baseline。目标是把“看起来协调”转化为可解释、可复用的视觉系统决策；它不决定页面 Section 的布局或业务模块构图。

## 决策顺序

按以下顺序建立视觉语言，避免先挑孤立色值或装饰样式：

```text
品牌与受众
→ 信息语气
→ 色彩角色与明度结构
→ 排版层级
→ 网格与空间尺度
→ Surface、边界与形状
→ 基础组件及状态
→ Design Board 组合验证
```

## 色彩系统

### 先定义角色，再选择颜色

至少区分：

- Brand：品牌识别，不等于所有按钮都使用品牌色；
- Text：标题、正文、弱化文字；
- Surface：页面底色、分区底色、容器底色与反色区域；
- Action：主操作、次操作、当前状态；
- Semantic：成功、警告、错误、信息；
- Border / Focus：边界、分隔与键盘焦点。

同一颜色不要承担互相矛盾的含义。高饱和色应稀缺，并与业务优先级一致。

### 用关系判断协调性

不要只问两个色相是否“搭配”，依次检查：

1. 明度：去色后，背景、内容、重点和状态仍能分层；
2. 饱和度：大面积通常低饱和，小面积才承担高强调；
3. 冷暖：确定稳定主调，另一温度作为有目的的对照；
4. 面积：强调色高频重复会失去强调能力；
5. 邻接：文字、边框、按钮与其真实背景关系清晰；
6. 语义：颜色与操作、状态和品牌含义一致；
7. 素材：UI 不与真实图片的亮度、色温和饱和度争抢。

`60–30–10` 只用于检查主次和面积，不要求精确比例或恰好三种色相。普通文本对比度至少 `4.5:1`，大文本至少 `3:1`，关键非文本界面元素通常至少 `3:1`；通过对比度不等于视觉协调。

## 排版系统

- 字体选择应匹配品牌语气、内容语言、字符覆盖和可读性，而不是只追求个性。
- 使用有限层级：Display / H1–H3 / Body / Small / Label，避免每个组件创造新字号。
- 同层级保持字号、字重、行高和颜色一致；强调优先使用一到两种信号。
- 正文行长与行高应支持连续阅读；长标题换行后仍保持重心和层级。
- 字号比例是起点，不机械套用固定数学比例；真实内容和语言长度可以修正。

## 网格与空间

- Container、列网格、Gutter 和 Spacing Scale 应形成有限尺度族。
- 用“组内小、组间大”表达关系；空间是信息结构，不是填充。
- 对齐线应稳定，避免组件各自选择独立宽度和起点。
- 响应式规则定义内容如何重组，不只定义桌面数值如何缩小。
- 留白必须帮助聚焦、分组或节奏；内容不足时不要用巨大空白伪造高级感。

## Surface、形状与组件

- Surface 层级应有限；背景换色必须表达分区、层级或叙事变化。
- Border、Shadow、Radius 只在关系需要时使用；若移除后关系仍清楚，应优先简化。
- 相同外观必须表达相同功能；同一区域通常只有一个最高强调操作。
- Hover、Focus、Active、Disabled 应属于同一状态体系，Focus 不能为了美观而省略。
- Card、Button、Tabs、Table 等基础组件共享相同空间、边界与强调逻辑，但不要求外观完全相同。

## Design Board 组合验证

Design Board 不是色票展示。审查时同时查看组件组合和整体页面，回答：

- 第一焦点是否明确，高注意力颜色是否被多个组件滥用；
- 灰度下是否仍有稳定层级；
- 冷暖、明度和饱和度是否与示例素材冲突；
- 字体、空间、圆角、边框和阴影是否像同一个系统；
- 基础组件能否直接指导 UI Architect，而无需重新猜状态和层级；
- 是否把未在真实页面验证的偏好错误写成 `Locked`。

发现单个组件问题时修正组件规则；多个组件出现同类问题时修正 token 或语义角色。需要改变页面任务、模块结构或媒体主次的问题不在此处理，交给 `website-ui-architect`。

## 输出要求

重要决定应记录“角色 / 原因 / 使用边界 / 状态”，不要只记录色值或尺寸。例如：

```text
Accent role: 仅用于主 CTA、当前状态和少量业务信号
Reason: 与冷色主调形成稀缺的行动提示
Boundary: 不用于轮播箭头、大面积背景或普通图标
Status: Flexible，待首个完整页面验证
```
