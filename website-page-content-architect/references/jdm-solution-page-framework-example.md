# JDM Solution Page Framework Example

这是由用户提供的 JDM 页面内容框架整理出的详细分析示例，用于理解复杂页面背后的判断过程，不代表默认交付格式。普通页面应按照 `SKILL.md` 输出精简的 UI-ready Page Content Framework，不复制本文件中的完整分析表。它不是 JDM、B2B 制造业或其他页面的固定模板；其中业务能力、时间、知识产权、交付和质量主张都必须由实际项目重新验证。

```text
STATUS: Example / Not project approval
MODE: New Page
PAGE: JDM Joint Development Solution
PAGE SLUG: jdm-joint-development-solution
```

## PAGE BRIEF

- **PAGE TYPE**：B2B 制造业解决方案页。
- **TARGET ROLES**：新品项目负责人、硬件/结构工程师、采购与供应链负责人。
- **AWARENESS**：访客可能知道 OEM/ODM，但不一定理解 JDM 或一站式机电协同。
- **PAGE JOB**：解释 JDM 的适用场景、协作方式与交付闭环，帮助合适项目发起需求沟通。
- **OFFER**：从产品定义、结构与电子协同，到制造、组装、测试和量产交付的联合开发服务。
- **PRIMARY CONVERSION**：提交项目需求。
- **TRANSITIONAL CONVERSION**：预约工程沟通或查看服务能力；是否提供下载资料取决于真实资产。

## EVIDENCE INVENTORY

### Candidate Facts — Require Verification

- 是否具备结构设计、电子硬件设计、PCB、SMT、CNC、注塑、钣金、3D 打印、组装与测试的真实闭环能力。
- 客户是否始终拥有全部知识产权，以及适用合同和 NDA 条款。
- 是否能够从概念阶段进入并衔接批量生产。
- 各流程周期、响应时间、质量承诺和适用行业。

### Evidence Needed

- 可公开的联合开发案例、版本迭代记录或量产结果。
- 结构与电子团队协同工作的真实资料。
- DFM、装配、测试与质量流程证据。
- 可公开的设备、认证、测试报告或客户评价。

### Evidence Gap

- 当前没有已验证的 JDM 客户案例。若案例对高风险联合开发服务的信任判断具有明显价值，可规划为 `Recommended` Section，先定义所需案例内容与建议位置；真实资料到位前不生成客户、项目结果或量化文案。

## NARRATIVE STRATEGY

采用 **Problem + Mechanism + Process + Proof**：访客先识别碎片化研发和供应链问题，再理解 JDM 与替代模式的差别，随后确认协作流程、能力边界与风险保障，最后进入需求沟通。

不采用纯公司能力列表开场，因为页面首先需要解决“JDM 是什么、为什么适合当前新品项目”的认知问题。

## SECTION MAP

### 1. `solution-jdm-positioning`

- **SECTION TITLE**：JDM 联合开发解决方案。
- **SECTION JOB**：在首屏完成业务匹配和行动引导。
- **VISITOR QUESTION**：你们提供什么，我的项目是否适合？
- **KEY MESSAGE**：客户主导产品定义，供应商协同完成机电研发和制造落地。
- **CONTENT POINTS**：适用项目阶段、服务范围摘要、一个可信差异点、主要 CTA。
- **CONTENT BOUNDARY**：不在首屏列出全部工艺、流程和保障条款。
- **PROOF / EVIDENCE**：需要一条可验证的闭环能力或项目事实；没有时使用克制定位。
- **CTA**：提交项目需求；可选预约工程沟通。
- **ROLE**：Page-specific / Detail。
- **ASSET NEED**：能够证明协同工作的真实项目或团队素材；无素材时不指定视觉替代品。

### 2. `solution-jdm-problems`

- **SECTION TITLE**：新品研发为何容易在机电协同和供应链中断层。
- **SECTION JOB**：让目标访客确认页面理解其现实问题。
- **VISITOR QUESTION**：你们理解我为什么难以把概念变成稳定成品吗？
- **KEY MESSAGE**：设计割裂、多供应商责任边界、可制造性不足和验证缺口会放大研发风险。
- **CONTENT POINTS**：合并相近问题，保留 3–5 个有明确差异的问题：机电冲突、供应链碎片、量产可行性、验证与交付断层。
- **CONTENT BOUNDARY**：不提前重复解决方案优势。
- **PROOF / EVIDENCE**：客户访谈、售前问题或项目复盘；没有证据时标为待验证客户假设。
- **CTA**：通常不需要按钮，可自然进入解决机制。
- **ROLE**：Page-specific / Detail。
- **ASSET NEED**：无强制素材。

### 3. `solution-jdm-definition-comparison`

- **SECTION TITLE**：JDM 如何工作，与 OEM、ODM 或后置优化有何不同。
- **SECTION JOB**：解释机制并避免模式混淆。
- **VISITOR QUESTION**：这和普通代工、整包设计或按图优化有什么不同？
- **KEY MESSAGE**：差异在客户参与程度、介入阶段、工程协同和交付责任边界。
- **CONTENT POINTS**：JDM 定义；只比较目标客户真正会混淆的替代模式；说明适用和不适用情形。
- **CONTENT BOUNDARY**：不做未经行业定义验证的绝对判断，不重复所有服务能力。
- **PROOF / EVIDENCE**：企业真实服务流程、合同边界和交付物。
- **CTA**：可链接服务范围或启动条件。
- **ROLE**：Page-specific / Detail。
- **ASSET NEED**：无强制素材。

### 4. `solution-jdm-workflow`

- **SECTION TITLE**：从需求评估到量产交付的协同流程。
- **SECTION JOB**：降低复杂项目对协作、进度和责任不确定性的担忧。
- **VISITOR QUESTION**：项目如何启动、评审、验证和定型？
- **KEY MESSAGE**：每个阶段都有明确输入、协作活动和可验证输出。
- **CONTENT POINTS**：需求评估、联合方案、DFM 评审、试样验证、迭代固化、试产或交付；每步说明输出而非只列动作。
- **CONTENT BOUNDARY**：具体天数只有在企业可以稳定承诺时才写入。
- **PROOF / EVIDENCE**：流程文档、评审清单、版本记录和交付样例。
- **CTA**：提交资料以启动评估。
- **ROLE**：Reusable with page-specific data / Detail。
- **ASSET NEED**：真实流程输出物；不指定时间线视觉形式。

### 5. `solution-jdm-capability-scope`

- **SECTION TITLE**：协同设计、制造集成与验证交付能力。
- **SECTION JOB**：说明服务范围和边界，帮助技术与采购角色判断匹配度。
- **VISITOR QUESTION**：哪些环节可以由你们完成，哪些需要客户或伙伴参与？
- **KEY MESSAGE**：能力按项目阶段组织，而不是无层级罗列工艺。
- **CONTENT POINTS**：方案协同、机械/电子制造、集成测试与交付；每类说明输入、输出、限制和可选能力。
- **CONTENT BOUNDARY**：完整材料、设备和工艺参数进入对应详情页。
- **PROOF / EVIDENCE**：能力清单、设备、团队和项目证据。
- **CTA**：查看相关能力或提交项目要求。
- **ROLE**：Page-family shared + page-specific boundaries / Preview。
- **ASSET NEED**：可验证的制造与测试资料。

### 6. `solution-jdm-differentiation`

- **SECTION TITLE**：联合开发的核心价值。
- **SECTION JOB**：把能力翻译为客户结果，并集中说明真实差异。
- **VISITOR QUESTION**：为什么这种协作方式比多供应商拼接更适合我的项目？
- **KEY MESSAGE**：整机级协同、DFM 前置、单一责任窗口和可追溯迭代可以降低项目断层风险。
- **CONTENT POINTS**：只保留有证据支持的 3–5 个差异点；每个差异点绑定客户结果和证据。
- **CONTENT BOUNDARY**：不再次完整重复流程或服务矩阵。
- **PROOF / EVIDENCE**：项目数据、版本记录、真实案例或流程资产。
- **CTA**：通常不需要独立按钮。
- **ROLE**：Page-specific / Detail。
- **ASSET NEED**：与每个差异点直接相关的证据。

### 7. `solution-jdm-risk-assurance`

- **SECTION TITLE**：项目治理、知识产权与质量风险如何控制。
- **SECTION JOB**：处理高客单联合研发中的合作顾虑。
- **VISITOR QUESTION**：产权、版本、质量和责任如何得到保障？
- **KEY MESSAGE**：保障必须来自明确机制和合同事实，而不是重复“全程兜底”。
- **CONTENT POINTS**：沟通责任、版本追踪、NDA/IP、质量验证、问题闭环；不存在的保障不写。
- **CONTENT BOUNDARY**：不重复“全链路能力”，不承诺无限责任。
- **PROOF / EVIDENCE**：合同条款、质量流程、版本系统和售后规则。
- **CTA**：可预约项目范围确认。
- **ROLE**：Reusable policy + page-specific explanation / Detail。
- **ASSET NEED**：流程或合规文件摘要。

### 8. `solution-jdm-objections`

- **SECTION TITLE**：启动 JDM 项目前常见问题。
- **SECTION JOB**：处理真实存在且尚未被前文回答的高频异议。
- **VISITOR QUESTION**：没有完整图纸能否启动、产权如何处理、如何衔接试产？
- **KEY MESSAGE**：启动条件、客户责任和供应商边界清晰可判断。
- **CONTENT POINTS**：只保留来源于销售、客户或项目团队的真实问题；删除与前文完全重复的回答。
- **CONTENT BOUNDARY**：不把 FAQ 当作未组织内容的收纳区。
- **PROOF / EVIDENCE**：真实咨询记录和已确认政策。
- **CTA**：联系团队确认未覆盖问题。
- **ROLE**：Page-specific / Detail。
- **ASSET NEED**：无。

### 9. `shared-project-inquiry-cta`

- **SECTION TITLE**：讨论你的新品开发需求。
- **SECTION JOB**：明确页面唯一主要下一步。
- **VISITOR QUESTION**：我需要准备什么，提交后会发生什么？
- **KEY MESSAGE**：提供基础需求即可进入初步匹配或评估，具体承诺以真实流程为准。
- **CONTENT POINTS**：所需资料、提交动作、下一步说明和隐私提示。
- **CONTENT BOUNDARY**：不新增页面前文未解释的新服务或承诺。
- **PROOF / EVIDENCE**：真实表单字段、响应流程和隐私政策。
- **CTA**：提交项目需求。
- **ROLE**：Reusable / Detail。
- **ASSET NEED**：无强制素材。

## DUPLICATION / CONFLICT REVIEW

- 将原稿中两组重复的“合作保障体系”收口为 Section 7。
- Section 5 负责能力范围，Section 6 负责有证据的差异价值，Section 7 负责治理和风险，三者不得互相复制。
- 案例模块按信任价值评估为 `Recommended`；框架记录所需客户背景、项目挑战、协作过程和可公开结果，由用户决定当前阶段是否启用，真实资料到位前不写访客可见案例。
- 流程时长、“24 小时匹配工程师”、知识产权和全权兜底等表述均需要企业确认，不能作为默认事实。

## CONTENT GAPS

- 真实 JDM 案例和可公开结果。
- 各阶段稳定可承诺的时间与输出物。
- 客户、供应商和合作方的责任边界。
- 知识产权、NDA、质量与售后政策。
- 能力范围、限制和批量生产条件。

## HANDOFF

下游 UI 应继承本示例的 Section Job、顺序、内容边界和证据状态，再为每个确认模块选择视觉 Form 与 Canonical Module Slug。不得通过视觉设计把 Evidence Gap 伪装成案例、数据或认证。
